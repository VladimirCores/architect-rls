# ADR-0003: Аутентификация через Basic Auth

**Дата:** 2026-09-17
**Статус:** Accepted (заменяет ранее предложенный JWT access/refresh)
**Теги:** security, backend

---

## Контекст

Изначально планировались JWT access + refresh с проактивным обновлением, httpOnly-cookie для web, secure storage для desktop. Это добавляет сложность: refresh-очередь, отзыв, cookie-политики, CORS с credentials. Для тренажёра с относительно короткими сессиями это избыточно.

## Рассмотренные варианты

1. **JWT access + refresh** — стандарт, но много инфраструктуры.
2. **Basic Auth (выбран)** — простота, одинаково на desktop и web.
3. **Session cookie** — просто на web, но неудобно на desktop.

## Решение

**Basic Auth. Токены не используются.**

- Клиент хранит логин/пароль **в памяти** на время сессии.
- **Каждый запрос несёт `Authorization: Basic <base64(login:password)>`.**
  - Сервер валидирует `Host`/`Origin`: разрешён `localhost` и `127.0.0.1` (dev); на сервере — свой домен. Неизвестный origin — 401.
  - Локально: лёгкий rate-limit (max 30 запросов/мин на uid) — защита от brute-force в соседней вкладке.
- **Каждая новая сессия требует логин** (старт приложения, перезагрузка вкладки).
- Logout = очистка памяти.
- Бан = невозможность залогиниться.
- Смена пароля — через `POST /actions/changepassword` (инициирует сам пользователь).
- Логин не может содержать `:` (разделитель credentials в Basic Auth по RFC 7617). Валидация при регистрации и смене пароля.
- Полный профиль (features, права) загружается после входа через `GET /profile`.

### Пароли

- Минимум **8 символов**. Валидация длины при регистрации и смене пароля (серверная, не только UI).
- **argon2id** (встроен в Bun).
- Параметры (OWASP-рекомендация для интерактивного логина):
  - `memoryCost = 65536` (64 MiB)
  - `timeCost = 3`
  - `parallelism = 1`
  - `hashLength = 32`
- Пароли никогда не хранятся в plaintext/обратимо.
- **Lockout:** после 5 неудачных попыток входа с одного uid — пауза 30 с, экспоненциальный рост до максимума 5 мин. Сброс при успешном входе.

### Роуты

- `POST /login` — проверка логина/пароля, возврат базового профиля (uid, роль).
- `POST /logout` — инвалидация сессии на сервере (при необходимости), очистка памяти на клиенте.
- `GET /profile` — полный профиль (права, features).
- `GET /admin/users/:id` — профиль пользователя (только админ; поля те же, что в `/profile`, дополняются).
- `POST /actions/changepassword` — смена пароля самим пользователем.

### Роль admin

- Логин `admin` зарезервирован, запрещён для регистрации и входа под общим UI.
- На экране `/login` — галочка «Войти как Администратор», при которой скрывается поле логина.
- Регистрации пользователей нет — создаёт админ через отдельный UI.
- **Первый запуск:** при пустой таблице пользователей единственный допустимый логин — `admin`; пароль задаётся через переменную окружения `INITIAL_ADMIN_PASSWORD` (одноразовый, сбрасывается после первого входа).

## Следствия

**Положительные:**
- ✅ Радикальное упрощение: нет refresh-логики, cookie-политик, отзыва, очередей.
- ✅ Работает одинаково на desktop и web.

**Отрицательные / риски:**
- ⚠️ Пароль в памяти клиента — при XSS на web может быть украден. Trade-off принят осознанно.
- ⚠️ Basic Auth поверх HTTP небезопасен — обязателен HTTPS на сервере.
- ⚠️ Нет granular revocation на уровне access — но при Basic это не имеет смысла.
