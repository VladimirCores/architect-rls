# ADR-0026: Оставить Bun + Hono + Drizzle на backend; Dart-сервер — не в scope

**Дата:** 2026-09-29
**Статус:** Accepted
**Автор:** Cores (консультация: Carson, Winston)
**Связанные ADR:** ADR-0001, ADR-0005, ADR-0016, ADR-0017
**Теги:** backend, api, architecture

---

## Контекст

На этапе планирования рассматривалась замена backend-стека Bun + Hono + Drizzle (TypeScript) на Dart-сервер (shelf / serverpod). Мотивация — единый язык на всём стеке: frontend уже Flutter (desktop), и будущая web-версия — это **тот же Flutter-клиент, скомпилированный в SPA** (см. ADR-0016). То есть весь клиент навсегда на Dart.

Цель — найти самый простой путь для будущих улучшений, переиспользования и долгосрочной поддержки решения.

## Рассмотренные варианты

1. **Оставить Bun + Hono + Drizzle (выбран)** — текущий стек, зафиксирован в ADR-0001.
   - Плюсы: рабочий contract-first пайплайн (orval → Hono-роуты + Zod, ADR-0005); спека OpenAPI — источник истины; зрелая экосистема TS; переиспользование моделей на клиенте уже решено через `openapi-generator-cli` (dart-dio).
   - Минусы: два языка на проекте (TS backend, Dart frontend).

2. **Dart-сервер (shelf / serverpod)** — единый язык на всём стеке.
   - Плюсы: один язык (Dart) от API до UI; прямое шаринг моделей/доменной логики между клиентом и сервером; Dart AOT хорошо подходит для real-time симуляции (тики ~16 мс).
   - Минусы: нет зрелого генератора OpenAPI → Dart-сервер (роуты/валидацию пришлось бы писать вручную); экосистема Dart-сервера меньше (нет аналога Drizzle); ломается зафиксированный contract-first пайплайн ADR-0005; переписывание уже существующего кода backend.

## Решение

**Оставить Bun + Hono + Drizzle (TypeScript) на backend.**

- Переиспользование и будущая поддержка обеспечиваются **API-контрактом (OpenAPI 3.1 в `swagger/`)** как источником истины, а не языком сервера. Клиентские модели уже генерируются из спеки — единый язык на клиенте не требует Dart-сервера.
- Замена стека на Dart-сервер — это риск поддержки (тонкая серверная экосистема) и потеря зрелого contract-first пайплайна, при этом выигрыш («один язык») уже частично достигнут через генерацию клиента из спеки.
- **Пересмотр условия:** вернуться к вопросу о Dart-сервере только если появится зрелый генератор OpenAPI → Dart-сервер (аналог orval для Dart) или если экосистема Dart-сервера существенно вырастет.

**Уточнение (2026-09-29):** рассматривается замена frontend Flutter (desktop + web) на **Vue 3 + Tauri**. Это не меняет решение по backend: стек становится целиком TypeScript (Vue 3 + Bun/Hono), что **усиливает** выбор Bun и полностью снимает мотивацию для Dart-сервера. Влияние — на frontend-решения: ADR-0001, ADR-0015, ADR-0016, ADR-0018 (см. OPEN-QUESTIONS).

## Следствия

**Положительные:**
- ✅ Сохранён рабочий contract-first пайплайн (orval → Hono/Zod, ADR-0005).
- ✅ OpenAPI-спека остаётся единым источником истины для desktop и web (ADR-0017).
- ✅ Shared Dart-модели на клиенте сохраняются через генерацию из спеки.
- ✅ Boring technology: зрелая, стабильная экосистема TS, проще найм и поддержка.

**Отрицательные / риски:**
- ⚠️ Два языка на проекте (TS backend, Dart frontend) — команда должна знать оба.
- ⚠️ Если в будущем появится зрелый Dart-серверный стек с OpenAPI-генерацией, миграция потребует переписывания backend (зафиксировано как условие пересмотра).

**Нейтральные:**
- Решение не блокирует future web-версию: тот же Flutter-клиент работает с теми же контрактами.
