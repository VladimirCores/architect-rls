# ADR-0020: Поток данных клиент-сервер (REST + WebSocket)

**Дата:** 2026-09-17
**Статус:** Accepted
**Теги:** backend, frontend, transport

---

## Контекст

Клиент получает координаты до 1000 boids в около-реальном времени и отправляет действия оператора (пометки, смену статусов). Нужно определить транспорт для каждого типа данных и обеспечить консистентность.

## Решение

- **Server-authoritative.** Сервер — единственный источник истины для состояния симуляции. Клиент рендерит то, что получает, и не выводит состояние независимо.
- **REST** — для статусов и действий: `POST /actions/boids/mark`, `POST /actions/boids/status`, etc. Ответ подтверждает применение.
- **WebSocket** — для координат boids (бинарный формат, см. ADR-0009).
- **Оптимизация:** неактивные/остановившиеся boids **не передаются** по WebSocket.
  - Клиент сохраняет их локально и продолжает отображать на карте.
  - Статус boid получается через REST (при изменении), не через WS-поток координат.
- **Бинарный формат WS** (Float32Array) — см. ADR-0009.
- **Интервал:** `INTERACTIVE_UPDATE = 16` мс (≈60 Гц).

## Следствия

**Положительные:**
- ✅ Снижение нагрузки на WS при неактивных boids (значительная часть популяции).
- ✅ REST для статусов — простая идемпотентность, точная привязка к tick.

**Отрицательные / риски:**
- ⚠️ Клиент должен отслеживать, какие boids «заморожены» локально и не получают обновлений (риск рассинхронизации).
- ⚠️ `boids.remove` при смене статуса на неактивный — клиент должен не удалить объект, а перевести в локальное состояние.
