# ADR-0013: Жизненный цикл локального backend

**Дата:** 2026-09-17
**Статус:** Accepted
**Теги:** backend, frontend, infra

---

## Контекст

Backend поставляется как часть desktop-приложения. Нужно решить, как он стартует, как выбирает порт, как завершается и где пишет логи.

## Решение

- Backend поставляется как **скомпилированный Bun-бинарник** в `assets/backend/<platform>/`.
- **Старт:** Flutter извлекает бинарник во временную директорию и запускает как дочерний процесс. ENV-переменные (`DEPLOYMENT_TYPE`, `MAP_TILES`) передаются при спавне; приоритет ENV над вшитыми константами — см. ADR-0002. При обнаружении `status=failed` в `_migrations` (ADR-0006) backend выводит диагностику и ожидает вмешательства оператора.
- **Стоп:** Flutter завершает процесс при закрытии приложения.
- **Порт:** фиксированный; если не задан — **динамический через handshake по stdout** (backend пишет `READY port=N`, Flutter парсит). Таймаут ожидания READY — **5 с**, иначе краш/перезапуск. Перед спавном Flutter проверяет, не занят ли порт (probe); если занят — завершает зомби-процесс и переиспользует порт.
- **Логи:** только в **файл**, лимит **10 МБ** на сессию. При достижении лимита — ротация: текущий файл переименовывается с суффиксом `.1`, создаётся новый. В БД логи не пишутся.
  - `GET /logs` (ADR-0005) читает **хвост активного файла лога** — offset-пагинация `{items, total, offset}` (см. исключение в ADR-0007); отдельного хранилища логи не имеют.
- **Watchdog** (автозавершение backend при краше Flutter) — **задел на будущее**, не реализуется.

## Следствия

**Положительные:**
- ✅ Единый бинарник, кроссплатформенный через matrix-сборку.

**Отрицательные / риски:**
- ⚠️ Без watchdog возможны зомби-процессы — учитывать при эксплуатации.
- ⚠️ Антивирусы/гейткиперы могут блокировать неподписанные бинарники — при поставке в MVP решить.
