# ADR-0006: Версионирование и формат ошибок

**Дата:** 2026-09-17
**Статус:** Accepted
**Теги:** api, backend, data

---

## Контекст

Нужно заранее определить, как эволюционируют API и схема БД, и как клиент единообразно парсит ошибки.

## Решение

- **API-версия — `/api/v1`** с первого дня.
- **Формат ошибок — `application/problem+json`** (RFC 7807).
- **Версия схемы БД** — отдельная таблица `_migrations`. **Не связана** с версией API.
  - Формат: `name` (string), `applied_at` (timestamp), `checksum` (string — hash SQL миграции для детекта дрейфа), `status` (enum: `applied`/`failed`).
  - Отдельного флага `dirty` нет: прерванная миграция — строка `status=failed`, она блокирует последующие миграции до ручного решения.
  - Версия принадлежит backend (миграции применяются при старте на desktop, отдельным шагом в CI на сервере).
- Каждая миграция выполняется в транзакции: при ошибке откатывается, схема не остаётся частично применённой.
- При обнаружении `status=failed` на старте backend выводит диагностическое сообщение (имя миграции, checksum) и ожидает вмешательства оператора.

## Следствия

**Положительные:**
- ✅ API и БД эволюционируют независимо.
- ✅ Клиент парсит ошибки единообразно.

**Отрицательные / риски:**
- ⚠️ Сопоставление версий API ↔ БД — только в документации, вручную.
