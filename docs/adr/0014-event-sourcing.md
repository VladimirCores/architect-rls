# ADR-0014: Event sourcing для аналитики

**Дата:** 2026-09-17
**Статус:** Accepted
**Теги:** data, backend

---

## Контекст

Нужна запись и воспроизведение действий пользователя. Это фактически event sourcing, что влияет на схему аналитики и формат логов.

## Решение

- Все значимые действия пользователя и системы сохраняются как **события**.
- **Session Manager записывает события в реальном времени** по мере их возникновения (см. ADR-0021) — не батчем по окончании сессии.
- **Таблица `events`:**
  - `event_id` — incremental int (PK), уникален в пределах одной БД. Для глобальной уникальности (клиент → сервер) — `(client_id, seq)` или UUID.
  - `name` — string (канонический дискриминатор типа события).
  - `type` — int (производный от `name`; единый маппинг в коде; не самостоятельный фильтр).
  - `timestamp`.
  - `uid` — user id.
  - `idempotency_key` — string (клиентский UUID на запрос); unique constraint `(idempotency_key, uid)` предотвращает дубли на retry.
  - дополнительные поля — по мере необходимости.
- **Источники событий:**
  - Роуты `/actions/*` (основные).
  - Роут `POST /event` — для произвольных событий `{name: string, idempotency_key: uuid, ...}`.

### Событие `boid.marked`

- Возникает на `POST /actions/boids/mark` (см. ADR-0005).
- Payload: `simulation_id`, `boid_id` (**инстанс**, не id справочника), `value` (`dangerous|safe`), `ts`, `idempotency_key` (UUID клиента).
- `ts` — привязывается к **tick симуляции** (момент решения оператора), серверное время приёма — fallback и валидация. Tick — монотонный индекс; маппинг tick → wall-clock задаётся при записи и единый для кадров и `boid.marked`.
- Перемена решения = новое событие с другим `value`; проекция хранит последнее значение (события иммутабельны, last-write-wins).
- LWW по `ts` (tick); при равенстве `ts` — детерминированный tie-break по `event_id` (больший побеждает).
- Дубли на HTTP-ретрае предотвращаются уникальным ограничением `(idempotency_key, uid)`.
- `boid.marked` допустим только для boid'ов в running-сессии. Mark на не-running сессии (или несуществующий `boid_id`) отклоняется с 404.
- **Криптографическая подпись событий экзамена** (Ed25519) — **TODO** (см. OPEN-QUESTIONS.md).
- Метрика успешной сессии: % правильно определённых «специальных» boids — рассчитывается на основе событий, времени, параметров симуляции и **финального снапшота состояния boids** (сохраняется в analytics DB при завершении сессии; для реплея post-MVP — из `.rlsrec`).

## Следствия

**Положительные:**
- ✅ Полное воспроизведение сессий.
- ✅ Гибкая аналитика.

**Отрицательные / риски:**
- ⚠️ Схема событий должна быть спроектирована до застывания MVP — изменения дороги.
- ⚠️ Рост объёма данных — потребуется retention-политика.
- ⚠️ `name` — канонический дискриминатор; `type` — производный int. При добавлении нового типа нужно обновить маппинг в коде, иначе `type` не определён.

## Реплей (post-MVP) — направление

Зафиксированный вариант (2026-09-17): воспроизведение строится на **записи координат**, а не на пересчёте симуляции из событий.

- **Автономный файл записи `.rlsrec`** — единица обмена и переноса между машинами (инструктор воспроизводит сессию курсанта на другом стенде).
   - **Header:** session_id, параметры симуляции + seed, версия карты и стиля (`map_version`, `style_version`), контрольная сумма. Контрольная сумма охватывает header + тайлы + кадры (позиция в файле + размер блока).
   - **Тайлы:** вшивается отрисованная векторная часть карты — таблица с дедупликацией по z/x/y (+ hash), кадры ссылаются на неё. Реплей не зависит от тайлов целевой машины.
   - **Совместимость версий:** при воспроизведении `map_version` или `style_version` в `.rlsrec` не совпадают с текущей версией — реплей отклоняется с явным сообщением.
  - **Кадры:** для каждого boid — `boid_uid` (uint32) + Float32 географические координаты, группируются блоками, дельта-кодирование + zstd. Формат — зеркало WS-пейлоада (единый сериализатор).
- **Analytics DB** — только индекс: сессии (метаданные, путь к `.rlsrec`), события, метрики. Кадры в БД не пишутся.
- Пометка: **Decision-later** — реализация post-MVP. Схема `events` проектируется без закрытия двери на будущие `session_frames`.
