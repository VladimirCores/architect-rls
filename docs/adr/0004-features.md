# ADR-0004: Система features

**Дата:** 2026-09-17
**Статус:** Accepted
**Теги:** backend, security

---

## Контекст

Нужно динамически управлять доступом к частям UI и API. Features создаёт админ, но часть из них — базовая и должна существовать всегда.

## Решение

- Features — **динамический список** в БД: таблица `features` с колонкой `code` (уникальная).
- **Базовые features — строковые константы в коде** (не enum в БД, чтобы избежать миграции на каждую новую фичу). Сидируются миграцией.
- Проверка в коде: `requireFeature('radar.export')`.
- **Единый middleware** на все роуты.
  - При регистрации роута вызывается `requireFeature` с явным списком фич из таблицы `features`.
  - OpenAPI-спека содержит `x-features` как документацию; middleware не читает её из спеки (расширения `@hono/zod-openapi` недоступны в рантайме).
  - Декларативно, без ручного дублирования в коде маршрутов — список фич хранится в таблице `features` и привязывается к роуту при регистрации.

## Следствия

**Положительные:**
- ✅ Типизация фич в TS + динамика из админки.
- ✅ Одна точка проверки на API.

**Отрицательные / риски:**
- ⚠️ Нужно поддерживать синхронизацию между константами в коде и записями в БД (сидирование).
