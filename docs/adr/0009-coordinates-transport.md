# ADR-0009: Транспорт координат

**Дата:** 2026-09-17
**Статус:** Accepted
**Теги:** backend, frontend

---

## Контекст

Нужно передавать координаты до 1000 boids в около-реальном времени (≈60 Гц) с минимальной задержкой и без потери порядка.

## Рассмотренные варианты

1. **WebSocket + JSON** — просто, но накладные расходы на сериализацию.
2. **WebSocket + binary (выбран)** — минимальные накладные расходы, порядок и доставка гарантированы.
3. **UDP** — низкая задержка, но потеря/порядок не гарантированы, отдельный транспорт.

## Решение

- **Транспорт:** **WebSocket** (не UDP).
- **Формат:** **бинарный** (ArrayBuffer / Float32Array).
  - Каждый кадр: для каждого boid — `boid_uid` (uint32) + координаты (Float32, lat, lon).
  - Порядок бoidов в кадре не гарантирован; клиент идентифицирует boid по `boid_uid`.
  - **Add/remove:** отдельные сообщения `boids.add` (payload: `boid_uid`, начальные координаты) и `boids.remove` (payload: `boid_uid`). Клиент применяет их к текущему набору.
  - Сериализация — отдельные middleware на клиенте и сервере.
  - **Точность:** Float32 достаточен для ~7 значащих цифр; для крупных координат (высокие широты) деградация позиции — допустима в пределах ~1 м. При необходимости фиксированной точки — `int32` (lat*1e6).
- **Интервал:** `INTERACTIVE_UPDATE = 16` мс (≈60 Гц).
  - Значение `adaptive` — задел на будущее, не реализуется.
- **Нагрузка:** до 1000 boids.
  - Задел: передача **дельты** (только изменения) снизит нагрузку на порядок. В требования пока не входит.
  - **Backpressure:** при медленном потребителе — bounded send-buffer (drop-oldest), не допускать неограниченный рост памяти.

## Следствия

**Положительные:**
- ✅ Бинарный формат снижает нагрузку на сериализацию.
- ✅ WebSocket даёт гарантию доставки/порядка (в отличие от UDP).

**Отрицательные / риски:**
- ⚠️ 1000 boids × 60 Гц × 16 байт ≈ 960 КБ/с на клиента (с `boid_uid`). Дельта — следующий шаг оптимизации.
