# ADR-0011: Три базы данных

**Дата:** 2026-09-17
**Статус:** Accepted
**Теги:** data, backend

---

## Контекст

Разные жизненные циклы данных: карта — read-only, приложение — read/write с миграциями, аналитика — read/write с event sourcing. Нужна возможность быстро выгрузить логи/аналитику копированием.

## Решение

Три независимых хранилища.

### 11.1 Карта

- **MBTiles**, read-only, без миграций.
- Пайплайн: `Geofabrik .osm.pbf → planetiler → .mbtiles (vector) → /map/tiles`.
- Загружается при первом запуске / в CI на основе `MAP_TILES={region|manual}`.
  - `region` — имя файла из `assets/maps` или регион с Geofabrik.
  - `manual` — путь указывает пользователь.
- **Доступность регионов** определяется **сканированием директории карт при старте** (`MapProvider`, `infrastructure/`): найденный `.mbtiles` = доступный регион. Нуль дрейфа — список равен фактической поставке. Битый/обрезанный файл = недоступный регион (проверка metadata-таблицы и пробного чтения).
- **Метаданные регионов** (отображаемое имя, дефолт, сортировка) — по необходимости sidecar `regions.json` рядом с картами; fallback — имя файла.
- В `.env` — **только выбор** (`MAP_TILES`). Выбор ≠ доступность.
- **`SUPPORTED_REGIONS` как статический список в коде — отменён**: перекомпиляция при смене территорий, дрейф между backend/frontend, синхронизация без причины. Имена регионов валидируются константами в коде (семантика), сам перечень — из файловой системы.
- **Версия карты** — поле `version` в стандартной `metadata` MBTiles.
- Стиль карты — один, вшит во frontend, версионируется с ним.

### 11.2 Приложение

- **SQLite** (desktop) / **Postgres** (server), Drizzle как единый ORM.
- Данные: пользователи/профили, настройки, features, права, boids, РЛС.
- **JSON с базовыми настройками** может загружаться при первом запуске для инициализации.
- Миграции: схема и данные меняются. Версия — `_migrations`.

### 11.3 Аналитика

- **SQLite** (desktop) / **Postgres** (server).
- Сущности: сессии, симуляции, тренировки, экзамены, логи, активность.
- **Event sourcing** — см. ADR-0014.
- PII нет, только ID.

### Локальная раскладка (desktop)

Разделение app / analytics подтверждено и локально — два независимых SQLite-файла в одном каталоге данных приложения:
- `app.db` — приложение: пользователи, настройки, features, права, справочники boids/РЛС.
- `analytics.db` — аналитика: сессии, события, метрики.
- `recordings/` — реплей-файлы `.rlsrec` (ADR-0014), вне БД.

Миграции обеих схем — общая `_migrations`.

## Транзакции между БД

**Нет сквозных транзакций.** `db.batch` в Drizzle работает в пределах одного соединения/файла — он не охватывает `app.db` и `analytics.db` одновременно. Кросс-файловая консистентность обеспечивается через **компенсирующую сагу**:

1. Операция записывается в `app.db` первой.
2. Событие переносится в `analytics.db` (через `db.batch` внутри одного файла).
3. Если шаг 2 падает — приложение повторяет попытку на следующем тике или при перезапуске (replay из очереди непереданных событий).
4. При крахе процесса между шагами 1 и 2 — на старте перебираются непереданные записи и дописываются в `analytics.db`.

Это **eventual consistency**, не strong consistency. Для экзаменационных сессий допускается краткосрочное рассогласование (миллисекунды); для бэкапов — копирование файла `analytics.db` даёт снимок, который может отставать на один тик.

## Следствия

**Положительные:**
- ✅ Быстрый бэкап аналитики копированием файла (предварительно `wal_checkpoint(TRUNCATE)` или SQLite backup API).
- ✅ Разные команды/нагрузки могут развивать БД независимо.

**Отрицательные / риски:**
- ⚠️ Eventual consistency между `app.db` и `analytics.db` — последний тик может потеряться при краше между шагами 1 и 2; бэкап `analytics.db` отстаёт на один тик.
- ⚠️ Nightly GC по `EVENTS_RETENTION_DAYS` должен исключать open-ended сессии и сессии, на которые ссылаются реплеи (`.rlsrec`).
- ⚠️ Три хранилища на desktop — нагрузка на бэкап/миграции.
