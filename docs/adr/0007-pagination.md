# ADR-0007: Пагинация

**Дата:** 2026-09-17
**Статус:** Accepted
**Теги:** api, backend

---

## Контекст

Все списочные роуты (`/rls`, `/boids`, `/logs`, `/reports`, `/admin/users`, `/admin/features`) должны отдавать данные единообразно и защищаться от крайних случаев.

## Решение

- Формат ответа: `{items, total, page, size}`.
- Дефолт `size`: **20**.
- Лимит `size`: **max 200**.
- Поведение при `page < 1`: **ошибка 422** (problem+json).
- Поведение при `page > max` (превышение): **пустой `items`**, `total` без изменений.
- Сортировка: **обязательный** параметр `sort` (поле + направление, напр. `created_at:desc`); без `sort` — middleware отклоняет запрос 422. Стабильный порядок гарантируется через уникальный вторичный ключ (`event_id` или `id`) при равенстве primary sort.
- Крайние случаи (отрицательные, превышение max, нечисловые значения) — **единый middleware** на всех пагинированных роутах.
- **Исключение — `/logs`**: использует offset-пагинацию `{items, total, offset}` (лог-файл — append-only, cursor не применим); см. ADR-0013.
- **Bulk-эндпоинты** (напр. выгрузка экзамена): отдельный лимит (burst 100, window 1 с) или exempt-эндпоинт с отдельным rate-limit bucket.

## Следствия

**Положительные:**
- ✅ Единая логика для всех списков.
- ✅ UI может строить нормальную пагинацию благодаря `total`.

**Отрицательные / риски:**
- ⚠️ Курсорная пагинация не поддерживается; для больших лент может понадобиться отдельный формат.
